# Capability-Status Matrix

**The spine of this repository:** one row per Microsoft AI-security capability, with its release status, a primary-source URL, and the date the status was last verified against that source.

> **Read `docs/how-to-read-status.md` first** if you are unsure what GA / Public Preview / Roadmap / Requires further validation mean here, or how each status is sourced.
>
> **Statuses change.** Verify any row whose last-verified date is older than the current monthly refresh window, and confirm contested rows in your own tenant before relying on them.

## Status legend

| Label | Meaning |
|---|---|
| **GA** | Generally Available per Microsoft primary sources (Microsoft Learn without a preview qualifier, and/or Microsoft 365 Roadmap status "Launched"). |
| **Public Preview** | Microsoft primary sources label the capability preview (e.g. a "(preview)" qualifier on Microsoft Learn). Preview terms apply — see `docs/how-to-read-status.md`. |
| **Roadmap** | Announced with a Microsoft 365 Roadmap entry; not yet rolling out. |
| **Requires further validation** | Microsoft's own sources conflict or the status cannot be confirmed from primary sources alone; verify in your own tenant before relying on it. |

## Row details

### Row 1 — Sensitivity-label processing restriction

- **What it does:** DLP policies using the **Microsoft 365 Copilot and Copilot Chat** location with the **Content contains > Sensitivity labels** condition exclude labeled items from being processed. Per Microsoft Learn: "Identified items still appear in the citations of the response, but the content of the item isn't used in the response or accessed by Copilot."
- **Status evidence (verified 2026-08-07):** the Learn section "Block files and emails with sensitivity labels from being processed" carries **no preview qualifier** and states "This feature is available in Microsoft 365 Copilot, Copilot Chat, and Copilot in Word, Excel, PowerPoint."
- **Source-wording change at this refresh:** on 2026-07-14 the same section additionally stated "This protection also extends to prebuilt agents in Microsoft 365 Copilot and Copilot Chat." That sentence is **no longer present** on the page as of 2026-08-07. The row's status is unaffected — the section still carries no preview qualifier — but **prebuilt-agent coverage should no longer be claimed from this source**. Confirm agent coverage in your own tenant before relying on it.
- **Caveats (from the same Learn page, verified 2026-08-07):**
  - Emails are covered only if **sent on or after January 1, 2025**; calendar invites are **not** supported.
  - When a labeled file is open in Word/Excel/PowerPoint under such a policy, Copilot skills in those apps are disabled; certain experiences that don't reference file content "aren't currently blocked."
- **Configuration reality (applies to rows 1–3 and 5):** the Copilot location is available **only in the Custom policy template**, and "when you select the Microsoft 365 Copilot and Copilot Chat policy location, **all other locations for that policy are disabled**." Policy updates can take up to four hours to take effect.

### Row 2 — External web search block on sensitive prompts

- **What it does:** a rule with **Content contains > Sensitive information types** and the action **Prevent Copilot from processing content > Performing Web Searches** stops Copilot from sending prompts containing configured SITs to external web search providers; responses continue from permitted internal Microsoft 365 sources.
- **Status evidence (verified 2026-08-07):**
  - The Learn section "Block sensitive information types in web search" carries **no preview qualifier**.
  - Microsoft 365 Roadmap feature **548671** shows status **"Launched"** with availability **June CY2026** (the Roadmap defines Launched as "fully released updates that are now generally available for applicable customers"). Confirmed via the public roadmap and Microsoft's public release-communications API for feature 548671; the API record was last modified **2026-06-12**.
- **History / caveats:** this sub-capability rolled out later than row 1 and was tracked in the Message Center as **MC1263277** (Message Center posts are tenant-scoped and have no public URL — cite the Roadmap ID publicly). Per the Roadmap description it "currently extends to Microsoft 365 Copilot and agents built in Copilot Studio that are published to Microsoft 365 Copilot." **Confirm availability in your own tenant** — regional/tenant rollout can lag a Launched status.

### Row 3 — Typed-prompt SIT blocking

- **What it does:** a rule with **Content contains > Sensitive information types** and the action **Restrict Copilot from processing content > Processing prompts** prevents Copilot from returning a response when the typed prompt contains configured SITs.
- **Why "Requires further validation":** Microsoft's own sources have described this sub-capability's status inconsistently (Ignite-era Microsoft blog coverage described it as entering GA while Microsoft Learn labeled it preview). As of **2026-08-07** the disagreement sits **inside a single Learn page**:
  - The section heading **no longer carries the "(preview)" qualifier** it carried on 2026-07-14. It now reads "**Block sensitive information types in prompts**".
  - The body of that same section is **unchanged** and still states, verbatim: "This feature is in preview and is rolling out to all tenants with access to Microsoft 365 Copilot and Copilot Chat. Check whether rollout has reached your tenant."
- **The dropped heading qualifier is not evidence of GA.** A removed qualifier sitting alongside an unchanged "This feature is in preview" sentence is precisely the conflicting-source condition this label exists for. The status therefore **holds at Requires further validation** on this refresh rather than moving to GA.
- **Do not record this row as GA.** Verify the rollout state in your own tenant. Treat this row as GA only when the page's own body text stops describing the feature as in preview **and** the behavior is confirmed in-tenant.
- **Scanning-scope caveat (verified 2026-08-07, Learn, verbatim):** "DLP can't scan the contents of files that you upload directly into prompts, so evaluation of the uploaded file for sensitive data doesn't occur. **DLP only checks the text you type into the prompt itself.**" Treat "what gets scanned" as a question to confirm at each verification pass, not an assumption.
- **Preview UX caveat (Learn):** during preview, blocking messages in Word/Excel/PowerPoint "might not clearly state" that the interaction was blocked by policy — the prompt is still restricted.

### Row 4 — Defender for AI scope boundary

- **What it does:** Microsoft Defender for Cloud's **AI threat protection** (Defender for AI Services plan) provides runtime threat detection for **Azure-hosted AI workloads** — per Learn, supported services are **Azure OpenAI supported models** and **Azure AI Model Inference service supported models**; alerts cover threats such as jailbreak, wallet abuse, data exposure, and suspicious access patterns.
- **Status evidence (verified 2026-08-07):**
  - The Learn availability table states **"Release state: Generally available (GA)."**
  - Defender for Cloud release-notes archive, May 2025: "**General Availability for Defender for AI Services** — May 1, 2025."
  - Defender for Cloud release notes: "**Threat protection for AI agents (Preview)** — … threat protection for AI agents built with Foundry, available in **preview** as part of the Defender for AI Services plan." The release-notes index lists this entry under both **February 2, 2026** and **February 3, 2026**; the matrix records the earlier date.
  - The availability table's **Feature availability** cell lists only "Activity monitoring (security alerts)" and "Prompt evidence (security alerts)" — it does **not** enumerate AI-agent protection. Agent coverage is evidenced by the release notes above, not by this table.
- **Common misconception — the scope boundary this row exists to document:** Defender for AI protects **Azure-hosted / Foundry model workloads only**. It does **not** cover **Microsoft 365 Copilot** and does **not** cover **GitHub Copilot**. Drawing Defender for AI as blanket "AI coverage" on an architecture diagram is a product-boundary error: M365 Copilot risk is addressed through Defender XDR and Microsoft Purview capabilities (rows 6–9 cover the Purview DSPM, shadow-AI discovery and Sentinel ingestion pieces, and row 10 covers what the Defender advanced-hunting surface does and does not reach).
- **Additional Learn caveats (verified 2026-08-07):** text tokens only (image/audio tokens aren't scanned); commercial clouds only — the availability table records **Azure Government: No**, **21Vianet: No**, and **Connected AWS accounts: No**; enabling at subscription level requires Owner or equivalent data-action roles.
- **Sources:** [AI threat protection (Learn)](https://learn.microsoft.com/en-us/azure/defender-for-cloud/ai-threat-protection) · [Defender for Cloud release notes](https://learn.microsoft.com/en-us/azure/defender-for-cloud/release-notes) · [release-notes archive](https://learn.microsoft.com/en-us/azure/defender-for-cloud/release-notes-archive).

### Row 5 — External-email grounding block

- **What it does:** a rule using the **Microsoft 365 Copilot and Copilot Chat** location with the **Email is received from > External users** condition excludes externally-sent email from Copilot grounding. Per Microsoft Learn: "When the policy detects that an email was received from a sender outside your organization's accepted domains, Copilot excludes that email from grounding, summarization, and citation. Copilot continues to use internal Microsoft 365 data sources where permitted, and the user's access to the email itself isn't affected."
- **Status evidence (verified 2026-08-07):** the Learn section heading carries a preview qualifier — "**Block external email from being processed (preview)**" — and the body states "This feature is in preview. It applies to Microsoft 365 Copilot and Copilot Chat, including email summarization and reasoning experiences that use email data." Preview terms apply; see [`docs/how-to-read-status.md`](../docs/how-to-read-status.md).
- **Why this row is a prompt-injection control, not a data-leakage control:** the other DLP-for-Copilot rows restrict what *leaves*. This one restricts what *enters* the model's grounding set. Per Learn, "This protection helps organizations reduce the risk of prompt injection and untrusted data influence."
- **Scope caveat — read before treating this as XPIA coverage (Learn, verbatim):** "The policy evaluates email metadata only - specifically, the sender domain compared against your tenant's accepted domains. **The body of the email isn't inspected.**" It is a sender-domain trust boundary, not content inspection: injected instructions inside an email from an *accepted* domain are not addressed by this control.
- **New at the 2026-08-07 refresh.** This sub-capability was not present in the matrix at v0.1.0 and was found by re-reading the row 1–3 source page. Confirm availability in your own tenant before relying on it.

### Row 6 — DSPM for AI licensing prerequisites

- **What this row is:** the *precondition* for every other DSPM-for-AI claim. Before asking what DSPM for AI shows you, a practitioner has to know what it costs and what entitlement turns it on. That question does not have a citable answer today.
- **Why "Requires further validation" — Microsoft's licensing references are circular (verified 2026-08-10):**
  - The current DSPM considerations page states only: "You have a supporting license for this Microsoft Purview solution, and your region is supported. For more information, see the Microsoft Purview service description." It names **no SKU**.
  - The Microsoft Purview service description, which that sentence points to, says: "For information about licensing about Microsoft Purview Data Security Posture Management for AI, see Considerations for deploying Microsoft Purview Data Security Posture Management for AI …" — pointing **back** at the *classic* DSPM for AI considerations article, which itself carries the same "see the Microsoft Purview service description" banner. The loop closes; it just closes through the classic page rather than the current one.
  - Neither endpoint of that loop states the entitlement. **A reader following Microsoft's own links cannot determine the licensing prerequisite**, which is precisely the "cannot be confirmed from primary sources alone" condition this label exists for.
  - *Axis note:* this row applies that label to the confirmability of a **licensing prerequisite** rather than to a release state, which is a slightly different axis from rows 1–5. The legend clause fits, and the Capability column names the licensing scope explicitly, but read the row as "the prerequisite is unverifiable", not "the product's release state is contested".
- **What Learn *does* state specifically (verified 2026-08-10, verbatim):**
  - "For Microsoft 365 Copilot and agents, users are assigned a license for Microsoft 365 Copilot." — a per-user entitlement for the Copilot/agent monitoring scope only.
  - "The enterprise version of Microsoft Purview data governance, to support the required APIs." — a scope-specific prerequisite for Copilot in Fabric and Security Copilot.
  - "For AI apps other than Microsoft 365 Copilot and Microsoft Facilitator, you've set up pay-as-you-go billing for your organization." — a **consumption** commercial model rather than a seat license. This bullet appears on the classic page and is **absent** from the current considerations page, which is itself part of the ambiguity.
- **Do not record a specific SKU for this row from memory or from a licensing comparison site.** The checklist's Group 3 expectation of an "E5 / E5 Compliance" citation is **not met by the current documentation** — that expectation should be treated as unverified, not as the answer.
- **Version caveat (applies to rows 6 and 7):** Learn currently carries two generations of this documentation. The pages titled "DSPM for AI" are marked classic: "This article is for the classic version of Data Security Posture Management for AI that's now replaced with a new version …" and "These improvements won't be added to this classic version". Confirm which version your tenant runs before applying either page's licensing text.

### Row 7 — DSPM for AI default posture

- **What it does:** DSPM for AI surfaces AI-usage and sensitive-data insights, and offers one-click preconfigured policies. The question this row answers is whether it **watches** or **enforces** by default — the single most common coverage-map error for this product.
- **Default posture evidence (verified 2026-08-10, verbatim). Every quote in this block is from [the classic DSPM for AI considerations page](https://learn.microsoft.com/en-us/purview/dspm-for-ai-considerations)** — named explicitly because these are the row's load-bearing quotes and they are *not* on the other two cited pages:
  - Browser paste/upload discovery: "This policy discovers sensitive content pasted or uploaded in Microsoft Edge, Chrome, and Firefox to AI sites. This policy covers all users and groups in your org **in audit mode only**."
  - Edge prompt collection: "This policy detects prompts sent to generative AI apps in Microsoft Edge and discovers sensitive information shared in prompt contents. This policy covers all users and groups in your organization **in audit mode only and doesn't capture content**."
  - The one policy that *can* block ships **not enforcing**: "This policy uses Adaptive Protection to give a block-with-override to elevated risky users … This policy covers all users and groups in your org **in test mode**."
  - Policies are **admin-activated, not automatic**: "Data Security Posture Management for AI provides some recommended preconfigured policies that you can activate with a single click."
  - The only thing that runs unprompted is assessment, not enforcement: "**No activation needed**, Data Security Posture Management for AI automatically runs a weekly data risk assessment for the top 100 SharePoint sites based on usage in your organization."
- **So: audit/monitor by default. It does not block by default.** Enforcement is a separate, deliberately activated policy plus endpoint onboarding.
- **Why the row is nevertheless "Requires further validation" — the primary ground:** the pages documenting the posture quoted above are the **classic** version, which Learn says is "now replaced with a new version that incorporates support for AI apps and agents, new features and broader reach" and to which "improvements won't be added". **No primary source establishes that the audit-mode-only default carries over unchanged to the replacement**, and that is squarely the legend's "cannot be confirmed from primary sources alone" condition. Note that the classic page carries no "(preview)" qualifier on the product itself, so a naive legend reading would push this row toward GA — the row deliberately resists that, because the documented behaviour belongs to a superseded version.
- **A secondary, weaker signal — stated precisely, because it is easy to overstate:** the Purview-and-AI article is internally inconsistent about DSPM's release state. One sentence reads "… in DSPM for AI and the AI activities tab in activity explorer from the **preview version** of DSPM"; another reads "… in the **current version of DSPM** and in DSPM for AI". Read in full, **neither phrase is applied to DSPM for AI** — both sentences name DSPM for AI as a *separate* surface alongside DSPM, so the preview/current inconsistency is about the broader posture-management product rather than about this row's capability. It is real and worth recording, but it is **not** the reason for this row's label; the classic-version ground above is.
- **Third-party AI site dependency (verified 2026-08-10, verbatim, same classic considerations page):** "Devices are onboarded to Microsoft Purview, required for: Gaining visibility into sensitive information that's shared with third-party generative AI sites." And: "The Microsoft Purview browser extension is deployed to **Windows** users and required to discover visits to third-party generative AI sites by using an Insider Risk Management policy. The browser extension is also required for Endpoint DLP policies on Windows when you use Chrome." Endpoint DLP enforcement against AI sites is scoped to "**Windows computers that are onboarded to Microsoft Purview**".

### Row 8 — Generative-AI app discovery (shadow AI)

- **What it does:** Defender for Cloud Apps' cloud app catalog classifies discovered applications, and generative-AI applications are a first-class category — so shadow-AI discovery is a filter over existing Cloud Discovery rather than a separate product.
- **Status evidence (verified 2026-08-10):** across five Learn pages read for this row — the catalog/risk-score page, Cloud Discovery setup, the product overview, the Shadow IT tutorial and the Defender for Endpoint integration page — there is **no "(preview)" qualifier on any relevant heading and no release-state sentence of any kind**. Per this repository's legend, Microsoft Learn without a preview qualifier is the GA signal. The capability is described in the present tense as available functionality.
- **Catalog scope (Learn, verbatim):** "The Microsoft Defender for Cloud Apps Cloud app catalog page provides a full list of over 31,000 discoverable cloud apps." The **Generative AI** category is defined as "Cloud apps that can generate digital media content such text, images, videos, and so on, using generative AI models." Two further AI categories also appear in the same (alphabetised) category table — **AI – MCP Server**, "Public cloud services that implement the Model Context Protocol (MCP) to coordinate interactions between AI agents and systems…", and **AI – Model Provider**, "Cloud-based platforms or APIs that deliver access to foundation models or large language models…". Both category descriptions are quoted from their opening clause; the trailing ellipsis marks where each sentence continues.
- **Terminology caveat worth knowing before you search:** across the **six Defender for Cloud Apps pages read for this row** (catalog/risk-score, Cloud Discovery setup, discovered apps, the product overview, the Shadow IT tutorial and the Defender for Endpoint integration page), Microsoft Learn does **not** use the phrase "shadow AI" once, and none of them links to an article dedicated to generative-AI app discovery. The capability is evidenced only by the catalog category table on the page cited. *Scope of that claim:* it is bounded to those six pages — it is strong evidence, not proof of absence across the whole product doc set.
- **Platform-coverage caveat — the source omits, rather than denies (verified 2026-08-10):** the discovered-apps page states "Supported apps include **Windows and macOS** apps, which are both listed under the Defender - managed endpoints stream", and the integration page's prerequisites list macOS with a minimum agent version. But the *same* integration page's "How it works" section describes the agent "when it runs on **Windows**" and Shadow IT discovery "across the **Windows** devices on your network" — an overview scoped to Windows that omits macOS rather than contradicting it. **Windows coverage is unambiguous; macOS coverage is stated in two places and silently omitted in a third.** Confirm macOS discovery in your own tenant before relying on it. The status label is unaffected — this is a scope question, not a release-state one.
- **macOS limitations Learn does state (verbatim):** "To support integrations for macOS apps, you must turn on network protection capabilities in Microsoft Defender for Endpoint. Since network protection only audits TCP connection close events, **UDP protocols aren't covered for macOS support**." And: "Customers integrating with macOS devices may observe a spike in CPU consumption."
- **What it cannot see (Learn, verbatim):** "By default, Defender for Cloud Apps can't discover apps that aren't in the catalog" (catalog/risk-score page). Endpoint-based discovery also requires devices onboarded to Microsoft Defender for Endpoint; for anything else, "it's important to deploy the Defender for Cloud Apps log collector on your firewalls and other proxies" (Shadow IT tutorial page — one of the six read for this row, not among the two cited in the table).
- **Licensing prerequisites (plan names only, per Learn):** a Microsoft Defender for Cloud Apps license, plus — for endpoint-based discovery — Microsoft Defender for Endpoint with Plan 2, or Microsoft Defender for Business.

### Row 9 — Sentinel Microsoft Copilot connector

- **What it does:** a Microsoft Sentinel data connector that ingests Copilot audit activity. Per Learn: "The Microsoft Copilot logs connector in Microsoft Sentinel enables seamless ingestion of Copilot-generated activity logs from M365 Copilot and Security Copilot into Microsoft Sentinel for advanced threat detection, investigation and response." It "uses the Office Management API to get your Microsoft Copilot audit logs", and the destination Log Analytics table is named CopilotActivity.
- **Why "Requires further validation" — the source contradicts itself (verified 2026-08-10):**
  - A page-level notice states: "Note that Microsoft Sentinel data connectors are **currently in Preview**. The Azure Preview Supplemental Terms include additional legal terms that apply to Azure features that are in beta, preview, or otherwise not yet released into general availability." That is a blanket claim over the whole class.
  - Yet the **same page** marks individual connectors with a "(Preview)" suffix in the entry title — for example "Microsoft Defender for Office 365 (Preview)". If the blanket notice were operative, per-entry labelling would be redundant.

The connector is named "**Microsoft Copilot**" and its description spans "M365 Copilot **and Security Copilot**", so it is not Microsoft-365-Copilot-exclusive. Detection technology is a filterable property in Threat Explorer and real-time detections and Advanced Hunting." That page carries **no preview qualifier**, and its "Applies to" line names Defender for Office 365 Plan 2 and Defender XDR. **This is an email-channel control** — it detects injection attempts arriving as mail, not injection inside a Copilot conversation.

### Row 11 — Conditional Access for workload identities

- **What it does:** Conditional Access policies can be scoped to workload identities — service principals — rather than to users, which is the control most often reached for when someone asks how to constrain an AI application's or agent's access.
- **The scope boundary, and the reason this row matters (verified 2026-08-10, verbatim).** From [the workload-identity article's Overview note](https://learn.microsoft.com/en-us/entra/identity/conditional-access/workload-identity): "Policy can be applied to single tenant service principals that are registered in your tenant. Microsoft and third-party SaaS applications, including multitenant apps, are not covered by these policies." [The users-and-groups assignment article](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-users-groups), under its "Workload identities" heading, states the same rule and carries the tail: "…are not covered by these policies. Managed identities aren't covered by policy." **The wordings are near-identical but not identical** — the first says "Policy can be applied", the second "Conditional Access policies can be applied" — so do not cross-attribute a quote between them. **The two corroborate rather than conflict**, which is why this row carries a status at all.
- **Status evidence, stated precisely because an earlier draft of this row got it wrong.** That draft claimed neither page carries a preview qualifier. **An independent re-verification pass falsified that**: the users-and-groups article has been rewritten to cover agents, its title now reads "Conditional Access: Users, groups, agents, and workload identities", and it carries an "Agents (Preview)" heading. The GA label survives, but on the narrower and correct basis: **that qualifier scopes to the Agents section, and the article's "Workload identities" section carries none**, as does the workload-identity article throughout. *Scope of that claim:* bounded to the sections retrieved on 2026-08-10. Because that page was substantively rewritten, any assertion built against an older revision of it deserves re-checking.
- **Prerequisite (a plan name, not a count — verbatim):** "Workload Identities Premium licenses are required to create or modify Conditional Access policies scoped to service principals. In directories without appropriate licenses, existing Conditional Access policies for workload identities continue to function, but can't be modified."
- **Two corrections to this repository's own prior expectation, both of which the checklist previously stated more confidently than the sources support:**
  - **"Or by custom-security-attribute filter" is not documented for workload identities.** Attribute targeting was found on [the Conditional Access for agents article](https://learn.microsoft.com/en-us/entra/identity/conditional-access/agent-id) — "Custom security attributes let you categorize **agent identities** and resources with business-specific labels, then target those attributes in Conditional Access policies" — which is a different, newer surface. The article previously assumed to document a workload-identity filter returned **HTTP 404** on 2026-08-10.
  - **No page read names the Microsoft 365 Copilot service principal at all.** The claim that it "appears excluded" is an *inference* from the generic sentence about Microsoft and multitenant apps — a reasonable one, but an inference, not a stated exclusion. The only Copilot mention found is a different thing entirely: "Some agents run directly from the cloud similar to SaaS applications (for example, Copilot Studio hosted agents) with no associated device."
- **The agent path is partly preview — quoted from, and attributed to, [the target-agent-identities how-to](https://learn.microsoft.com/en-us/entra/identity/conditional-access/howto-target-agent-identities), under "Considerations for selecting agent assignments"** (verbatim): "The **agent users** option targets agents' user accounts. This option is currently in Preview." **That page is named explicitly because an earlier draft of this row attributed this quote to the Conditional Access for agents article, which does not contain it** — a re-verification pass caught it. It is the same cross-attribution defect this repository had to correct in v0.1.1, which is why every quote here now names its own page. The agents article does carry the unsupported-configuration list, including "Policies targeting all users don't include agent's user accounts."
- **One sub-claim that is genuinely unsettled, and is therefore *not* asserted:** the users-and-groups article labels agent scoping as "Agents (Preview)" as a class, while the how-to tags only the *agent users* options as Preview and leaves the agent-identity options untagged. **Which agent-targeting options are in preview cannot be determined from these pages** — treat that sub-question as requiring in-tenant confirmation. It does not affect the service-principal capability this row labels.
- **The limit that decides whether this control is worth anything for AI workloads (verbatim):** "Conditional Access only protects resources secured by Microsoft Entra ID. For example, if an agent accesses resources using an API key, it bypasses the Microsoft Entra ID authentication and token issuance pipeline entirely and Conditional Access policies won't apply to them." An agent authenticating with a key is outside this control entirely.

### Row 12 — GitHub Copilot policy management

- **What it does:** Copilot feature, model and privacy settings are governed by policy at the **enterprise** level and the **organization** level, set by enterprise owners and organization owners respectively, for the Copilot Business and Copilot Enterprise plans.
- **Why "Requires further validation" — and this row is a worked example of a status claim failing its own verification.** An earlier draft labelled it **GA** on the ground that no page carried a preview qualifier. An independent re-verification pass dismantled that reasoning in three places, and the row is corrected rather than the finding buried:
  - **The GA sentence was misread.** "The MCP servers in Copilot policy controls use where MCP server support is generally available (GA)" attaches its GA predicate to *MCP server support* — it is a clause limiting **where the policy takes effect**, and it implies MCP support is *not* GA everywhere. It says nothing about the release state of policy management. It is no longer offered as evidence of anything but its own scope.
  - **The absence sweep was neither exhaustive nor clean.** The organization page carries a heading "Opting in to previews or feedback" and the text "Opt in to preview features: If enabled, users can test new Copilot features that are not yet generally available"; the policy-conflicts reference lists a policy row "Editor preview features". GitHub Docs *does* use explicit "(public preview)" suffixes elsewhere — so their absence on these pages is weaker evidence than it looks, not stronger.
  - **Two cited primary sources hedge the same rule differently.** On the multi-enterprise case the concepts page says the most restrictive policy "almost always applies"; the policy-conflicts reference says it "usually applies" and names exceptions the concepts page does not. That is a disagreement between two sources this row cites, on the rule practitioners most need to be right about.
  - **And "policy management" is an umbrella**, not one feature: it spans many individual policies whose release states plainly differ. A single label over all of them would be a category error even if the evidence were cleaner.
- **What *is* solid:** everything quoted below about *how* precedence resolves was re-fetched and confirmed verbatim on the pages it is attributed to. The uncertainty is about the release **state**, not about the mechanics.
- **The precedence rule — and the correction this row exists to make.** This repository's checklist previously recorded that "more-restrictive precedence wins". **That is not what the documentation says, and the difference is operationally significant.** Three distinct rules apply:
  - **Enterprise over organization is absolute, not a restrictiveness contest (verbatim):** "If your enterprise owner has selected a specific policy, such as enabling a feature everywhere, disabling it everywhere, or enabling it for selected organizations only, you cannot override that setting at the organization level."
  - **Between organizations inside one enterprise, the *least* restrictive policy usually wins (verbatim):** "If these organizations have configured the same policy differently, the least restrictive policy usually applies, but there are some exceptions." Elaborated: "Least restrictive: if any of the organizations has enabled a feature, this feature is enabled for the user everywhere. This applies to all but the more sensitive Copilot features." Most-restrictive resolution "applies only to the most sensitive Copilot features, for example: access to Copilot metrics using the API."
  - **Across different enterprises, most restrictive nearly always wins — with the two sources hedging differently.** The concepts page: "if a user receives a license from multiple different enterprises, the most restrictive policy across enterprises almost always applies." The policy-conflicts reference states the same rule with "usually" and names exceptions. **Do not present either wording as settled**; this divergence is part of why the row carries its label.
  - **So resolution is per-policy and direction-dependent.** A coverage map that assumes one org's restriction protects a user who also holds a license from a more permissive org in the same enterprise is wrong by default.
- **Delegation, and a naming inconsistency worth knowing before you search (verified 2026-08-10):** enterprise owners may delegate a policy to organizations. The concepts page calls this "Let organizations decide"; the policy-conflicts reference calls the same control "No policy". Both terms are verbatim; expect to search for either.
- **Who policies actually bind (verbatim):** "Generally, policies only apply to users on your Copilot plan. A user is governed by the policies of the enterprise or organization where they receive a Copilot Business or Copilot Enterprise license." With a stated exception: "A small number of policies work differently and govern a setting for everyone. For example, you can block Copilot cloud agent for all users in your enterprise's repositories."
- **A default worth checking rather than assuming (verbatim):** "Suggestions matching public code is set to Blocked by default for Copilot Business users."
- **Sourcing note.** This is the first row in this matrix whose primary source is **not** Microsoft Learn or the Microsoft 365 Roadmap. GitHub Docs is admitted as a first-party documentation site for a Microsoft-owned product, and it is registered as a **human-only source**: no automated run fetches it, and the row is re-verified by a human at the monthly cadence. See [`docs/agent-cadence.md`](../docs/agent-cadence.md).
- **No version indicator.** None of the four pages renders a last-updated date, revision or version stamp, so the last-verified date here rests on the fetch date alone — one reason this row is human-refreshed.

### Row 13 — Enterprise governance of MCP servers

- **This row exists because this repository was wrong.** Both `checklists/capability-status-verification.md` and the matrix's planned-rows list previously committed to recording MCP governance as "**a gap, not a delivered control**" — VS Code-centric and bypassable. The 2026-08-10 verification pass found that **a real, non-overridable, cross-client enterprise control now exists**, so the planned framing was retired rather than written up. The gap has narrowed to a specific and stateable shape; it has not closed.
- **The control that does exist (verified 2026-08-10, verbatim, from [the enterprise MCP allowlist page](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-enterprise-allowlist)):** "You can define an allowlist and denylist to control which MCP servers users in your enterprise can run in Copilot clients. These lists are defined in your enterprise's `managed-settings.json`, which you can store on GitHub." Per [the MCP management concepts page](https://docs.github.com/en/copilot/concepts/mcp-management), this method "allows you to apply settings across clients that users cannot override", matching servers on "name, URL, or `stdio` commands".
- **Its evaluation order is precise, and deny wins (verbatim):** "1. Always allow built-in default servers, such as the built-in GitHub MCP server. 2. Block the server if it matches any entry in `deniedMcpServers`. 3. If `allowedMcpServers` is present, block the server if it does not match an entry. 4. Block the server if its URL or command contains an unresolved variable, such as `${VARIABLE}` or `$VARIABLE`, because the client cannot verify the server." Note bullet 1: **built-in default servers are a permanent carve-out** that no allowlist removes.
- **It fails closed, which is worth knowing and rare enough to record (verbatim):** "If an allowlist or denylist is malformed (for example, has invalid JSON), the client treats the policy as an empty `allowedMcpServers` list. This blocks all servers except built-in default servers." And: "If the client cannot determine a policy layer because of a retrieval or device-discovery error, it retains the previously enforced policy. The effective policy can become more restrictive, but not less restrictive."
- **Status evidence — two mechanisms, two states.** GitHub names the managed-settings method as the generally available one and the registry method as preview, verbatim, on [the MCP server access page](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-server-access): "This feature is in public preview and is not the recommended method for restricting access to MCP servers. The more secure, generally available method is to define settings in your enterprise's `managed-settings.json` file." Do not read one label over both.
- **The weaker mechanism says plainly that it can be bypassed** — from [the MCP allowlist enforcement reference](https://docs.github.com/en/copilot/reference/mcp-allowlist-enforcement), verbatim: "Enforcement is based only on server name/ID matching, which can be bypassed by editing configuration files. Strict enforcement that prevents installation of non-registry servers is not yet available." The concepts page describes the same method as "Less secure matching, based on name or ID only. Users can bypass the restriction by editing configuration files."
- **The scope boundary — this is what remains of the gap, and it is the reason not to draw MCP as "governed" on a coverage map:**
  - **Client coverage is bounded and still moving (verbatim):** supported clients are "Clients supported by the `managed-settings.json` file… Planned to expand in the near future." The page enumerating which clients those are was **not read on this pass**, so the actual coverage is *unverified here* — confirm it before relying on it.
  - **Third-party hosts are explicitly outside it (verbatim, GitHub Docs):** "This policy does not control access and permissions for the GitHub MCP server in third-party host applications (like Cursor, Windsurf or Claude)."
  - **Configuration surfaces are many and developer-initiated.** Per VS Code's documentation, MCP servers can be configured in a workspace `.vscode/mcp.json`, a user-profile `mcp.json`, a workspace `.mcp.json`, a user `~/.copilot/mcp-config.json`, the command palette, the CLI, dev-container customizations, and by automatic discovery from other applications. Across those flows the documented gate is a trust prompt, not an administrator — and VS Code warns that starting a server directly from `mcp.json` skips even that: "If you start the MCP server directly from the `mcp.json` file, you will not be prompted to trust the server configuration."
  - **The protocol itself is transport-agnostic**, so governance keyed to a URL or command has a moving target. Per the MCP specification, stdio servers run as a local subprocess — "The client launches the MCP server as a subprocess" — and implementers "MAY implement additional custom transport mechanisms". VS Code states the consequence directly: "Local MCP servers can run arbitrary code on your machine."
- **A second, editor-scoped control also exists**, delivered through Group Policy or MDM: VS Code's `ChatMCP` policy takes `all`, `registry` or `none` ("MCP server support is disabled"), and `McpGalleryServiceUrl` points at a private registry. Visual Studio states it "respects allow list policies set by organization administrators through GitHub". These are real, but they govern one editor each — which is precisely the distinction that made the old "VS Code-centric" framing right in its time and wrong now.
- **Sourcing note.** Like row 12, this row's primary sources are GitHub Docs, registered **human-only**: never fetched or adjudicated by automation, re-verified by a human at the monthly cadence. The VS Code and Model Context Protocol pages cited in this section are **not** primary sources for the status and are not registered — they are named inline so the scope claims above are checkable.
