# Changelog

All notable changes to this repository are recorded here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project follows a **monthly refresh cadence**: every row in the capability-status matrix is re-verified each month and every verification pass is recorded below (date, rows touched, status changes). What "re-verified" means differs by row, and the difference is stated rather than smoothed over: most rows are re-fetched from their pinned Microsoft Learn source by the automated cadence, while the Microsoft 365 Message Center, the GitHub Docs pages behind matrix rows 12 and 13, and the NIST and CSA cross-walk rows can only be re-read by a human — so their dates move when a person moves them, and not otherwise. See [`docs/agent-cadence.md`](docs/agent-cadence.md).

## [Unreleased] — 2026-09-11 refresh

### Fixed

- **The human-only containment gate stopped claiming a containment it does not provide.** `check_human_only_containment` inspects the watched `sources` array for `docs.github.com` entries and nothing else, so what it enforces is that **GitHub Docs** page content never reaches the model tier. The error message it emitted said **non-Learn** page content — a strictly larger claim, and a false one: the watched array is not Learn-only, with four entries fetching from `raw.githubusercontent.com`, one from the OWASP GenAI site and one from the public Microsoft 365 Roadmap, none of them Learn and none of them stopped by this gate. **The instructive part is where the false version lived.** The check's own docstring already said it is *"Scoped to GitHub Docs, not to 'non-Learn content'"* — and the message three lines below it claimed exactly that. The code documented the correct scope and published the wrong one, so no amount of reading the docstring would have caught it; only reading what the check *says when it fires* does. The same sentence was pasted verbatim into every staleness issue by `.github/workflows/stale-guard.yml`, which is how it reached a reader-facing surface at all. Corrected at all three sites, and pinned by two tests: one asserts the emitted error names GitHub Docs and never the word "non-Learn", and one scans the six published surfaces for the claim shape. **The scanner is matched on adjacency rather than co-occurrence** and deliberately crosses newlines, because the workflow builds the sentence from two consecutive `echo` lines — a line-scoped pattern would have seen neither half and passed vacuously, which is the defect class this release spent three review rounds on. A third test feeds it both shipped spellings, including the two-line form, so it is known to be load-bearing. The first run of the new scanner failed on the comment written to explain it, which is the check working.
- **`.gitignore` — the evidence bundle the *documented* local procedure writes was committable.** `evidence/` has been ignored since `47d99bd`, but that is the spelling the two bot workflows use. Both contributor-facing procedures — `docs/agent-cadence.md`'s "Running tiers D2 and D3 locally" and `CONTRIBUTING.md`'s baseline step — tell a human to run `--evidence-out evidence.json`, at the repository root, where no rule reached it: `git check-ignore evidence.json` returned 1. So following the published instructions left an untracked file full of text taken verbatim from upstream pages, sitting outside the automated-change allowlist and one `git add -A` away from being committed — the exact accident the `evidence/` rule exists to prevent, at the one path the rule missed. Ignored now under both spellings, and the test asks `git check-ignore` rather than reading `.gitignore` back, because reading the ignore file is transcription: it would pass on a rule that a later negation pattern overrides.
- **`scripts/validate_bot_pr.py` — `uncommitted_governed_changes` stopped justifying itself with a fact its own commit falsified, and that makes three.** The docstring explained why the probe is scoped to `GOVERNED_PATHS` by observing that both bot workflows leave an untracked evidence directory *"neither of which is gitignored"*, concluding that "the unscoped form was dirty on every single run". `47d99bd` added that sentence **and** the `.gitignore` rule for `evidence/`, so the run it describes never happened; `git log -S` puts both in the one commit. **The code is correct and is not touched here** — the scoping is right, only its stated reason was wrong — and the replacement rests on the design instead: an automated run may only write inside the allowlist, so only a governed path can hold the uncommitted write this probe hunts, while an unscoped `git status` would also trip on the root-level `evidence.json` of the bullet above, on a `watch.log` beside it, on an editor swap file, none of which is an uncommitted automated change. Revision 1 of this release's plan proposed changing this function's *behaviour* as well, making an empty diff an error under `--bot`; that was withdrawn as a deliberate non-goal, because the tri-state is a control — writing nothing is the correct automated outcome whenever the adjudicator's permission table requires an issue rather than a pull request — and reverting it would have manufactured a red daily run on the path operators most need to trust.
- **The same shape three times, and not one of the three was reachable by testing the code.** The `relevance_filter`'s page-level justification named a banner the rule never reached (retracted in the 2026-09 entries below); `check_human_only_containment`'s error message claimed a scope its own docstring three lines above correctly denied (the entry above); and this docstring cites an observation a line in the same commit made false. Every time, the behaviour was right and the explanation was wrong — which is exactly what an assertion about behaviour cannot catch. The standing lesson is written into the replacement docstring: **prefer a rationale that rests on the design over one that rests on an observation about the environment, because the second expires.** "That directory is untracked" stops being true the moment someone edits `.gitignore`; "this probe is about governed paths" does not. Pinned by `StatedRationaleTests`, whose own two vacuity failures are the argument for a positive control: the first pattern borrowed `[^.]` from the containment scanner and matched nothing, because the sentence it hunts names `evidence/evidence.json` and that filename's own dot ends the match; the second spelled "neither of which is" as a literal and went silent the moment the break test re-wrapped the paragraph by one word. Neither was caught by reading it. The detector now bounds on a paragraph rather than a sentence and treats every gap inside the claim as `\s+`, and a fourth test proves the retraction allowance — naming a withdrawn claim in order to withdraw it is legitimate, and this entry does it twice — is not a hole. Both fixes were verified by reverting them: the `.gitignore` line fails 1 test, the docstring 1. The suite is **249** tests.
- **Issue #27's Reproduction block published a `stale_guard.py` invocation that does not do what it claims.** It gives `--window-days 0` as the way to enumerate every dated item; the comparison is strict `age > window`, so a zero-day window reports only items stamped before today, which is why that run printed 5 of the 18. The enumerate-everything spelling is `--window-days -1`. Corrected by a comment on the closed issue rather than by reopening it — all four of its findings are fixed and shipped, and what was wrong is the instruction a reader would follow to reproduce them.

- **`scripts/watch_sources.py` — matrix row 9 has a working automated watch for the first time, and three defects in section extraction are why it never did (issue #31, finding 3).** The issue offered two remedies — build a body-scoped relevance mode, or concede the page cannot be watched and move it to `human_only_sources` — and neither is what shipped, because re-deriving the page showed the premise was wrong: this source *can* be watched, and the reason it wasn't is three separable faults, each fixed here and each pinned by a test that fails when it is reverted.
  **(1) Chrome is now removed before the page is split into sections.** Learn wraps its in-topic table of contents in `<nav aria-label="In this article">` around an `<h2>In this article</h2>`. `html_sections` split on headings while only `strip_html` removed chrome, so that navigation heading became a section boundary and took ownership of the article's lead-in — the intro paragraph and any page-wide release-state banner standing above the first authored heading. **This reached all 16 html sources:** `In this article` is the second heading of every one of them, and `relevance_scoped_text`'s "page-level text is always in scope" rule was therefore keeping 0.9%–8.0% of each page, all of it breadcrumbs, while the article's own lead-in sat one section below it and out of scope. That is the mechanical reason row 9's notice was unwatched, and the reason the rule's own stated justification was false — retracted above. `CHROME_ELEMENTS` is now the single place either path asks what is chrome, which is the property `section_headings` always claimed.
  **(2) Page-level is positional, not a heading level.** `PAGE_LEVEL` was read as "any heading at level 1", and the Sentinel page carries a mis-authored `<h1>NOTE - UPDATE:</h1>` buried inside one connector entry. It held **336,102 of that page's 1,084,895 characters — 31%** — permanently in scope, on the one source whose entire reason for declaring a filter is that an unfiltered fingerprint of it would move on nearly every run. Its stored phrase `deprecated` came from that out-of-scope connector text. Only the *first* heading is the title now; a stray heading deep in a document belongs to whatever entry contains it. Measured across the registry, this shape is unique to that page — every other html and markdown source has exactly one h1-level section — so nothing else moves.
  **(3) A collapsible entry is a section, and it is atomic.** The connector entries on that page are `<details>`/`<summary>` disclosures, not headings, which is why the declared filter matched **0 of 47 headings** and `filter_collapsed` had been warning about it since PR #28. Entry titles are now boundaries at a level below `<h4>`, so one always nests under the heading above it and can never be taken for the document title — **and everything inside an entry is that entry's body, headings and nested disclosures included.** That second half was not in the first draft of this change and an adversarial review found it: because a heading is always a *shallower* level than an entry, a heading placed inside a matched entry popped the entry off the scope stack and silently evicted the rest of its body. Measured on the live page, one `<h3>` inside the tracked entry took the scoped text from 5,184 to 4,010 characters **with the fingerprint unchanged**, so a "generally available" sentence under it went undetected while the identical sentence without the heading was caught. Not a hypothetical: **37 of that page's 46 authored headings already sit inside connector entries**, and the tracked one merely had none yet. A nested disclosure did the same thing for the same reason. Treating an entry as a leaf fixes both, and it is also what makes the mis-authored `<h1>` in defect (2) stop being page-level at the root rather than by rule. Disclosure nesting is measured with a balance scan that **fails open** — an unbalanced page stops being clipped rather than over-clipped, because refusing to clip merely restores the older, noisier behaviour while over-clipping would drop real entries with no sign anything was lost.
  Learn's own furniture is built from `<details class="popover">` and is excluded by that class — matched as *open tag immediately followed by its own `<summary>`*, after a first attempt that bounded each widget by searching forward for `</details>` and, on an unclosed one, ran into the next element and silently excluded a real entry. That is the failure this exclusion exists to prevent, reintroduced by the mechanism meant to prevent it, and it was caught by the test written for it rather than by review.
  **(4) Page-level standing belongs only to a heading at page level.** An interim version of defect (2)'s fix let *any* authored heading consume the document-title slot, on the theory that a level-1 heading appearing after other headings must be a stray. The same review measured the cost: a single `<h2>` above the article `<h1>` — one Learn template edit away — demoted the real title, so the page's lead-in left scope and row 9's banner vanished from the phrase set, reported only as a phrase *disappearing*.
